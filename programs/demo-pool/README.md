# programs/demo-pool

Anchor program. A minimal lending pool that lends test tokens on the
oracle's SAS attestation. It exists to show how a lender checks the
attestation, not as a real protocol: principal only, no interest, tenor or
liquidation.

Layouts, error codes and the exact check order: `docs/FORMATS.md` §14.

## Instructions

| Instruction | Who | What |
|---|---|---|
| `create_pool` | anyone (becomes admin) | creates a pool and its token vault: mint, SAS credential + schema, policy hash, tier limits, freshness limits, approved enclave builds |
| `update_pool` | admin | replaces the lending rules (not the mint, credential or schema) |
| `borrow` | borrower (a relayer may pay) | checks the attestation, sends up to the tier's limit, opens the one loan a borrower can have per pool |
| `repay` | borrower | returns the principal and closes the loan |

Several pools come from the same program: a pool is the PDA
`["pool", admin, [pool_id]]`. Two pools with different rules can lend on the
same attestation; nothing is verified twice.

## What `borrow` checks

The pool does **not** CPI to read the attestation. The account is passed
into `borrow` and read there (CPI is only used by `programs/oracle` to
*write* to SAS):

- the account is the SAS attestation of the signing borrower under the
  pool's credential and schema (the address is derived from those), owned by
  SAS, of the expected size and type;
- the oracle's SAS signer wrote it (anyone can create SAS attestations under
  their own credential);
- it hasn't expired, and it is within the pool's own limits for attestation
  age, statement age and statement length;
- its tier has a limit in this pool and the amount is within it;
- its `policy_hash` is the one the pool requires;
- the enclave build that produced it is approved by the pool **and** still
  active in the oracle registry.

The layout code comes from the oracle crate (`oracle::sas::parse_attestation`,
`oracle::attest::parse_payload`, `oracle::state::EnclaveEntry`), which this
program uses as a library (`features = ["cpi"]`).

## Token program

Classic SPL Token mints only (`anchor_spl::token`). `anchor-spl`'s
`token_2022` feature is on only because Anchor's `init` for a token account
needs it. Supporting Token-2022 later is a code change with no account
migration (FORMATS §14 → Token program), after deciding how to treat each
mint extension. The pool doesn't look at a mint's freeze authority: pick a
mint whose freeze authority you trust.

## A real lender

No existing Solana lending program can make a borrow depend on an outside
attestation without a code change. A production lender would add the checks
above to its own borrow path; marginfi-v2 (Apache-2.0, Anchor) is the kind
of program this is written for.

## Build, client, tests

```sh
anchor build                                   # target/deploy/demo_pool.so + target/idl/demo_pool.json
pnpm --filter @tio/demo-pool-client generate   # clients/ts/demo-pool/src/generated (committed)
cargo test -p demo-pool                        # the lending rules as pure functions
pnpm --filter @tio/demo-pool-tests test        # surfpool: real oracle + SAS binary + SPL Token
anchor test                                    # oracle and demo-pool suites
```

- The surfpool tests (`tests/`) reuse the oracle test harness
  (`@tio/oracle-tests`): every attestation they borrow on is submitted
  through the real oracle program first.
- The TypeScript client is generated by Codama from the IDL; CI fails if the
  committed client differs.
